# Repository Guidelines

## Location & Related Files

The code lives only in this local repository (`~/projects/a7-space-studio`); it moved out of Dropbox on 2026-09-11 because Dropbox must not sync `.git/`. Never move it back. Non-code materials (floor plans, furniture and lighting references, Street View captures, issue screenshots and supplier comparison sheets) live in `Dropbox/Agent/100_Todo/projects/a7-space-studio/`, whose `README.md` points back here. Keep this pointer and that one in sync if either location changes.

## Project Structure & Module Organization

This repository is a buildless Three.js apartment editor. The deployable application lives in `dist/`: `app.js` coordinates UI and persistence, `scene.js` owns Three.js rendering and navigation, `model.js` defines the A7 floor plan and furniture data, `geometry.js` contains low-level geometry helpers, `spatial.js` handles placement, clearance, doors, and routing, `finishes.js` holds the furniture board-finish catalogue and texture generator, `floorings.js` the separate SPC flooring catalogue (room floors only) and its plank, herringbone and tile generator, `surroundings.js` defines facade layouts, relief and painted surfaces for the view outside and lift lobby, `facade-geometry.js` creates the perforated roof canopy and side-wall rings, `share.js` encodes and decodes share links (the current layout in the `#plan=` URL fragment), `schemes.js` compares and merges design schemes by content, `cabinet-light.js` mounts linear lights on cabinet faces, and `recovery.js` sets aside a saved layout that fails to load and requests persistent storage. `plan-drawing.js` draws the 1:50 A3 plan sheet (SVG) that the 平面圖 button opens in a new tab. Styles and markup are in `dist/style.css` and `dist/index.html`. Keep reference drawings in `dist/assets/` and vendored Three.js files in `dist/vendor/`. Tests are in `tests/*.test.mjs`. `server.mjs` serves the static application locally.

## Build, Test, and Development Commands

- `npm install` installs the pinned development dependency from `package-lock.json` when needed.
- `node server.mjs` serves `dist/` at `http://127.0.0.1:4173` for local review.
- `npm test` runs all Node test files with the built-in test runner.

There is no compilation step. Changes under `dist/` are source changes and deployment output. Cloudflare Pages publishes the `dist` directory.

## Coding Style & Naming Conventions

Use browser-native ES modules, semicolons, and single-quoted JavaScript strings. Prefer `const`; use `let` only for reassigned state. Use camelCase for functions and variables, PascalCase for classes such as `SpaceScene`, and descriptive kebab-case IDs in HTML. Internal geometry uses metres; convert to centimetres only at UI boundaries. Keep rendering concerns in `scene.js`, floor-plan data in `model.js`, and reusable collision math outside UI handlers. For new multiline code, use two-space indentation. No formatter or linter is configured, so keep edits focused and follow nearby style.

## Testing Guidelines

Use `node:test` with `node:assert/strict`. Never `deepEqual` three.js objects or raycast hits: a failure prints the whole object graph and has OOM-killed the machine (11 GB); compare counts or ids. Name files by subsystem, for example `tests/navigation.test.mjs`, and describe behavior in each `test()` title. Add regression coverage for geometry, collision, camera, persistence, or interaction changes. Run `npm test` before committing. For visual or responsive changes, also review the local site at desktop and mobile widths.

## Commit & Pull Request Guidelines

Recent commits use short imperative subjects, such as `Fix kitchen door pivots and master corner`. Keep each commit limited to one coherent behavior. Pull requests should explain the user-visible change, identify affected views, list validation performed, and include before/after screenshots for 3D or responsive UI changes. Link an issue when one exists.

## Known Pitfalls

- Air conditioners (`airConditioner`, `acKind:'indoor'|'outdoor'`) are one furniture type with two catalogue entries. `air-conditioner-shape.js` is deliberately independent of model imports: `geometry.js` uses its `acBox`, so importing the mounting module there would make `EPS` uninitialised when a consumer imports geometry before model. `AC_UNITS` keeps the supplied body w/d/h; `AC_RACK` adds the outdoor rack envelope (photo-based 4 cm each side, 7.5 cm behind, 3.5 cm in front and 12 cm below). `elevation` is the assembly underside (the rack bottom outdoors), `spin` turns the whole assembly about its centre, and `acBox` is shared by collisions, camera obstacles and the plan footprint. The standard size fields still edit body dimensions. `air-conditioner-render.js` generates original geometry, including the indoor outlet vane and outdoor fan grille / rack; never commit the supplier photos or model names to the UI.
- `air-conditioner.js` checks wall solids in height as well as plan (including sills and lintels, unlike `wallRects`, which fills windows and drops lintels). Indoor full-back support uses coplanar surface rectangles swept by height and merged horizontally, so a window hole between supported corners cannot pass; indoors may use non-draft beam side faces. An outdoor rack only needs its two rails (`AC_RAILS`, `acRailSpans`, which the renderer also uses) in front of wall or balcony-railing faces (`railingSolids`, curb to `RAILING_TOP`), at any height (owner, 2026-10-05); `mountAirConditioner` slides it along a face until a rail reaches the end. In walk view the railing opening is open air above its top rail, so outdoor drags and placement use `railingSurface` (its inner face, curb to ceiling) when nothing nearer is under the pointer; sockets never do. Walk view targets go through `airSurface`/`airTarget` in `app.js`: a stacked unit under the pointer stands for its wall, `acOnSurface` mounts outdoor racks only on faces turned like the pointed one and within 10 cm of its plane (`mountAirConditioner` `facing`/`on`; sliding to wall contact in corners, where a rack may have under 1 mm of play), never on a door leaf (`surfaceAt` reports `action`), and `nearestClearHeight` fixes the height: stack gaps are millimetres taller than a unit, and a gap made by stopping a unit at contact fits another to within a micron, so it samples each gap's whole height with the floor (3.1 cm) and ceiling limits as bounds rather than trusting one computed height. A blocked move to another face must not keep the turn it started with: `guardedAirConditioner` returns the unit unchanged when its result has a new problem. Grille and vent lines have `raycast` disabled: three.js picks lines within 1 m by default, which made units grab nearby clicks. `guardedAirConditioner` refuses moves that deepen an existing overlap (`acDepth`), so a unit placed into a beam cannot be dragged further in. `mountAirConditioner` finds the nearest face and never uses an infinite extension of a short face or shrinks a unit to fit. A near miss stays a visible draft. `guardedAirConditioner` shares the wall-plane contact slider with sockets, checking support, rack-inclusive clashes, floor and ceiling; moves toward an invalid pointer position fall back to the current plane. Typed sizes grow centred, then from either end (`resizeAnchors`, width only), so a unit in a corner widens away from it. `syncHanging` rechecks all AC drafts before scene mutations, including moving / resizing / deleting their beam. Tests: `tests/air-conditioner.test.mjs` covers support gaps, beam edges, rails and the railing, two-way collisions, vertical stops, stacking and stack gaps (with the owner's exact `_10`/`_11` values), corners, picking, rotation, sharing and rendered bounds. Browser checks should also cover real pointer dragging on a beam, deleting / restoring its support, reload, and desktop / phone controls.

- A mesh with a single material ignores `geometry.groups`: every face is drawn. The unclipped beam box still calls `addGroup` for five faces, but its top face renders, and top view depends on it. Match what a mesh actually draws, not what its groups suggest.
- Do not fix coplanar seams with a depth offset. It only decides which surface wins, so the seam reappears on the other surface. Beams avoid seams geometrically instead (`beamVisiblePieces` / `beamGeometry` in `scene.js`); keep new solids that can hide beams in `ceilingOccluders`.
- Reproduce rendering bugs with the user's exported layout first. Resizing leaves sub-millimetre remainders that idealised test scenes never contain.
- In the Playwright MCP a page screenshot can hang on "waiting for fonts to load" (5 s timeout, every view). Capture the 3D view instead the way the 截圖 button does: patch `HTMLAnchorElement.prototype.click` for one call, click `#shot`, read the blob URL into a data URL and save it with `browser_evaluate`'s `filename` (it may only write under the working directory, so use `.playwright-mcp/` and delete it). Simpler, where `browser_run_code_unsafe` is available: `page.screenshot({clip,path})` with an absolute path writes anywhere (a scratch directory) and does not wait for the element to be stable; `locator.screenshot` can also time out on "waiting for element to be stable" while the 3D view keeps drawing. The MCP itself drops page snapshots and console logs into `.playwright-mcp/` under the session's working directory; when the session was started from the Dropbox project folder, delete that folder there afterwards. `app.js` exposes nothing on `window`; to set up a test scene write the layout into `localStorage['a7-studio-v1']` and reload, never into the user's own browser.
- Every edit path (drag, arrow-key nudge, handle resize, typed values) must share one exterior rule, `insideShell` in `model.js`: inside the outline *and* clear of the exterior walls' 12 cm thickness. When beam resizing checked only the outline, a beam could sit 6 cm inside a wall, and every later nudge was rejected because the start position already failed the rule.
- Lamp shadow maps are not redrawn every frame (`shadowMap.autoUpdate=false`). Scene methods that move, add, hide or relight geometry are wrapped at the end of `scene.js` to set `shadowsDirty`; door and cabinet animations request updates while they move. A new way of changing the scene must mark shadows dirty too, or shadows will lag behind it.
- The 3D view is drawn on demand (`frame` in `scene.js`): only when the camera moved, an opening is animating, shadows are dirty, or `requestRender(ms)` asked for it. The methods wrapped at the end of `scene.js`, texture arrival, clicks on controls, key and input events, and presses, wheel and pointer moves over the 3D view request a render (a press elsewhere, such as grabbing a floating window, does not). A new way of changing the scene that bypasses all of those must call `scene.requestRender()`, or the picture goes stale until the next input. Edits rebuild one item (`rebuildItem` in `app.js`, via `resizeItem`), not the whole flat; the list's warning dots are cached until the next `persist()`.
- Each shadow-casting light takes a texture unit in every lit material. Past `MAX_TEXTURE_IMAGE_UNITS` (16 on many GPUs, 32 in headless Chrome, so tests pass locally) textured materials fail to compile and silently vanish. `assignLampShadows` caps lamp shadows at `shadowBudget()`; keep any new shadow caster inside it.
- In walk view, lighting follows the room the camera is in (`lightRoom`, keeping the last room in a doorway). The ceiling `bounce` and the cove `coveFill` are single scene-wide lights, so there they add up only that room's lamps and coves (`updateRoomLight`); and a lamp in another room that casts no shadow would shine through walls, so `assignLampShadows` drops it to intensity 0 (not `visible=false`, which changes the light count and rebuilds every shader). Lamps that cast shadows are left alone, since walls and doors already stop them. The overview and top view keep the whole flat. Changes caused by moving (a new room, the shadow set following the view) go through `setLightLevel` with `fadeLights` on and ease in over about half a second (`stepLightFade` in `frame`, which keeps drawing while it runs); `updateLight` (switches, day/night) cancels fades and applies at once.
- Every light costs shading on every pixel, and a shadow-casting light costs more. RectAreaLights more than doubled frame time in walk view, so fixtures use spot lights; measure frame time before adding lights.
- The view outside (`dist/surroundings.js`) is an estimate: tower kinds from 2025 Street View, distances (18 m north, 8 m east) from the owner. A7's three north windows face the right third of the louvred tower opposite; the east neighbour shares A7's setback, so it must not reach north past A7's north face. The north facade has 1.35 m recessed balcony glazing, projecting piers, parapets and louvres; the east wall has contrasting tile bands, slit frames, three exhaust-fitting columns and a 1.25 m recessed platform stack to the right. The roof canopy lies horizontally with real holes. The right tower's rings and their dark slatted band belong at the centre of the exposed alley-facing side wall, flanked by window stacks; use `ringSideLayout` and `facadeRecess` for both painting and geometry rather than a corner offset. These dimensions are photo estimates. Paint and relief share their facade layout in `surroundings.js`; `scene.js` instances repeated parts by colour with vertex shading. Outside materials are unlit `MeshBasicMaterial` with painted day and night looks, so indoor lamps and bounce never light the neighbours and they cost no shadow texture units; keep it that way.
- Judge a finish colour on a sampled pixel, not by eye. The old sky-heavy hemisphere plus an unshadowed sun at 3.1 lit floors about 1.4x, so walnut rendered as light oak while the palette floor's dark texture hid it. Keep light from above close to light from below (a test checks the ratio).
- Door leaves turn about their hinge-side corner on the swing-side wall face (`doorLeaf` in `spatial.js`), not about the middle of their thickness; a mid-thickness pivot makes the hinge edge sweep through the jamb and look as if the hinge slides. Leaves fill the clear span between jambs; several openings (front door, bath A) start at a perpendicular wall, so `doorLeaf` probes `wallRects()` for the real jamb face instead of trusting the opening's ends. `doorRects` (swing limit against walls, walk-view obstacles) is built from `doorLeaf` too, so collision matches the drawn leaf and handles at every angle (until 2026-09-26 it was an older approximation 6-9 cm shorter than the leaf). Furniture inside a door's swing is a clash (`blocksDoor`: the leaf sampled every 2° up to its limit, solid up to the 2.1 m door height), reported by `issues` as `擋住…開啟範圍`. `model.js` and `spatial.js` import each other for this, so neither may use the other's exports at module top level.
- The clear ceiling height is `HEIGHT` in `model.js` (3.00 m since 2026-09-24, 2.79 m before). Anything that reaches the ceiling (walls, the balcony opening, curtain rod and fabric, beams, lights, pendant limits, the height input's maximum) must derive from `HEIGHT`; doors (2.1 m) and windows (sill 0.9 m, height 1.5 m) are architectural and stay absolute. Neighbouring towers use `SITE.floorHeight` (3.2 m floor to floor), which is independent. Tests should import `HEIGHT` rather than repeat the number.
- Ceiling items stack ceiling → beam → hanging cabinet → light (`ceilingRank` in `model.js`). An item whose whole footprint lies under a non-draft item of an earlier kind hangs from its underside (`mountedOn`); `mountDrop` adds up the hosts' heights, so a light under a cabinet under a beam drops by both. A partial overlap is a clash, never a mount, and the order never inverts, with one exception (2026-10-06): several hosts whose undersides are level (two 50 cm beams meeting end to end) and whose union covers the whole footprint carry it together (`mountHosts`, which samples the footprint about every centimetre); hosts at different levels or with a gap between them stay a clash. Use `mountHosts`/`hangsFrom`, not `mountedOn`, wherever the question is "does this hang from that". `refreshValidity` places each group from `mountOffset`: in walk and overview items sit at their real height (hanging cabinets at `hangingElevation`); top view inverts the stack so lower items stay clickable, drawing a cabinet under a beam just above the ceiling and a light above everything it hangs from. Only the light's fixture is lifted: `keepLampAtRealHeight` holds its lamps (spot and pendant point lights) at the real height, or they would light the tops of what the light was lifted over. Without that glow a pale fixture on a pale beam or cabinet is hard to find from above, so fixtures carry a thin dark rim (`topOutline`) shown only in top view; from below it would read as a halo on the ceiling. Hanging cabinets also store that height as `elevation`, refreshed before every scene build or move, for checks that see one item (door sweeps, walk camera); `issues` recomputes it rather than trusting the stored value. Anything that moves a beam or cabinet must still end in `refreshValidity` so what hangs below follows. Lights clash with floor furniture the way hanging cabinets do (`lightSpan`: from the underside of what they hang from to the fixture bottom, a pendant's cord included), and both sides report it; a light reaching below the floor is flagged like a cabinet stack taller than the room.
- `floorBoardRects()` leaves about a quarter of each room uncovered; the base slab shows through. A room with a chosen flooring (`floorings.js`) therefore gets one continuous `roomFloorGeometry` panel instead of boards or tiles.
- A flooring's `colors` are the 1st/5th/50th/95th/99th percentiles of the whole catalogue swatch, plank-to-plank differences included. `flooringPixels` therefore folds each plank's tone (`vary`) into the value *before* the rank mapping; multiplying a plank tone on afterwards widens the spread beyond what was measured. Comparison sheets against the catalogue live in the Dropbox `材質比對/地板比對-*.jpg`.
- Modular cabinet finishes have three levels: the cabinet's `finish` (sides, top and each column's lowest board), `partFinishes` for all `doors` (drawer and sliding fronts included), `shelves`, `backs` and `drawerBoxes`, then a cell's own `finishes.{door,shelf,back,drawerBox}`. An unset level follows the one above (`cellFinish` in `cabinet-design.js`). A cell's shelf is the board under it, and each cell has its own back panel. Validation migrates the first release's `body`/`fronts`/`interior` and a cell's single `finish`. Materials are cached per finish code, so cost grows with distinct finishes (about 0.65 s each to generate the first time), not with the number of parts.
- A corner shelf (`cornerShelf`) is a quarter ellipse whose square corner sits at the local back-right (`CylinderGeometry` θ from −90° to 0°, radius 1, scaled by w and d); its shelves are a one-column `cabinetDesign` of open cells (each cell's shelf is the board at its bottom), so the cabinet editor edits it with `shelvesOnly` set, which hides fronts, parts, columns, the bottom gap and multi-select and shows a top-board switch. `normalizeCornerShelf` clears any fronts before validating and converts the pre-2026-09-27 `shelves` list of shelf-top heights. `cap` adds a top board as thick as a shelf (`CORNER_BOARD`). Finishes follow `cellFinish` like cabinets: each shelf, and each cell's slice of both straight boards (wall side and cabinet side count as the back and are cut at every shelf), with base and top on the unit finish. Collision still uses the w × d rectangle.
- A beam fills the room from the ceiling down by its height (`beamReaches` in `model.js`, modelled as a hanging box like `lightReaches`), so floor furniture that reaches into it, such as a full-height wardrobe, clashes on both sides; coves keep their own `beamCoveClash`. Until 2026-09-27 beams were skipped entirely and a 3 m cabinet under a 50 cm beam showed nothing.
- Moves and resizes go through `addedProblem` in `spatial.js`: the first physical problem the changed item has that it did not have before (`issues(...,{doorSweeps:false})`, so door swings only warn and existing clashes never lock an item in place). `guardedMove` goes straight to the target when that is clear, otherwise to contact axis by axis in 5 cm steps plus bisection, naming what it touched rather than what is under the pointer; `largestFit` bisects a resize; `fitSize` finds the limit to a micrometre and rounds the dimension that changes most down to a whole millimetre measured from zero, so a stopped drag lands on the same size however fast or from whatever size it started (it once stepped whole centimetres from the current size and stopped at 87.1, 87.3 or 87.6 where 88 fit). Walls are compared one by one (`wallsHit` in `model.js`): the shared message 與牆體重疊 once let an item that touched one wall pass through every other. Drags, nudges, typed X/Z and sizes (`commitFurniture`, trying `resizeAnchors` centred and from either side), top-view edge drags (`fitSize`) and the cabinet editor's `checkFit` all use them. `clashes` in `geometry.js` rejects far-apart rectangles before the full signed distance, which made `issues` about 3x faster; drags depend on that speed.
- The `draft` flag (red frame in top view; since 2026-09-27 visible and solid in overview and walk) is saved with each item. Editing re-checks only the edited item and existing drafts, so `parseState` in `app.js` re-checks every item on load: after a plan change moved a wall, clashing items stayed unflagged until the owner touched them.
- A light cove (`cove`) is furniture with an `elevation` (HEIGHT − `coveGap` − board thickness), like panels and TVs, so floor-furniture, hanging-cabinet and light clash rules apply unchanged; beams are checked separately (`beamCoveClash`). Its light is not a light item: the ceiling and wall wash are additive `MeshBasicMaterial` planes over a shared greyscale ramp (`coveRamp`, `LinearFilter` because a `DataTexture` defaults to nearest and bands), the ceiling plane sits 1 cm down with a stronger polygon offset than the ceiling's own, and it has no lamp: a point light under the ceiling painted a hot spot, so all switched-on coves feed one shared `coveFill` hemisphere light from above (warm sky, black ground), the reverse of the lamps' `bounce` from below, at 0.32 by day like the lamps. Coves do not feed `ceilingBounce`: that light comes from below and would brighten the ceiling rather than what a cove lights. Its `lightObjects` entry has no `point`, and `updateLight`/`assignLampShadows` skip that. Placement validates the new item, which is what gives a cove or panel its `elevation`; before that a new cove sat on the floor and clashed with sofas.
- There is no TV-wall object any more (removed 2026-09-26): a TV wall is a `panel` (back panel, carries `elevation` like TVs and hanging cabinets, finishable) plus ordinary cabinets and a TV, so every part edits like other furniture. `validateFurniture` expands a saved `mediaWall` item through `splitMediaWall` before validating (parts in front of the panel on the wall side; each part grows to its type's minimum rather than failing the whole layout; an upper module starting under 1 m becomes a `wardrobe` standing on the floor, raised on an empty bottom above the plinth, others a ceiling-hung `hangingCabinet`) and drops its construction notes. A wall-hung TV does not clash with a panel (`tvOnPanel`).
- A TV sits in a cabinet cell either hung (`tvMount:'niche'`) or standing on the cell's shelf (`tvMount:'cabinet'` with `supportCell`; without it, on the cabinet top). Both are re-placed from the cabinet on every commit, drag and cabinet edit (`nicheTvPlacement`/`shelfTvPlacement`), are exempt from clashing with it (`hostsNicheTv`), and are only warned about when they do not fit (`nicheTvWarnings`): never resized, since the owner sets sizes from real models, and never marked draft, so they stay visible. Defaults come from `bestTvCell`: the open cell the TV fits whose TV centre is nearest 1.1 m, else the largest open cell; a TV on a cabinet stands on the top only when the cabinet is at most 1.2 m and the TV clears the ceiling.
- Fronts and cells are separate: `design.doorGroups` lists cells sharing one hinged door over their combined rectangle (`frontPanels` yields one panel per door, keyed for open state by its first cell; `mergeDoorCells`/`splitDoorGroup` edit them). Members mirror front, `handle` and door finish; validation silently drops a group that is no longer a rectangle of matching hinged cells, so splits, deletes and line moves never need to maintain groups. Drawers never span cells (their boxes would hit inner boards). Sliding doors may (since 2026-09-29; `groupFronts` = `hingedFronts` + sliding): a shared sliding door's leaves run inside the carcass across the whole door like a single cell's, and every board inside its rectangle (shelves, part dividers, side panels between columns) stops `SLIDE_SETBACK` (5.5 cm) short of the front for the tracks, while the boards on its edges stay full depth and carry them (`slideDoors`/`upright` in `makeModularCabinet`). The owner chose this over leaves hung in front of the carcass, which would stand about 4 cm proud of the neighbouring doors. Handles are drawn only when a cell has `handle:true`; the editor has no template picker, `cabinetTemplates` only seeds new cabinets. Two handleless fronts (2026-10-06, `handleless`; validation drops their `handle`): `grooved` is a double door whose right leaf has a finger slot cut into its edge at the middle (`GROOVE`, measured on the owner's photo: 3 cm wide, 1.5-61.4 % of the door height), drawn as the leaf around the slot plus a thin dark lining behind it, since the carcass seen through the slot is lit like the door and the cut was invisible; `sliding4` is four leaves (min 1 m), the middle pair on the rear track and the outer pair in front. Sliding leaves (`slideLeaves` in `scene.js`) carry a travel for each way of opening: `openCells` 2 opens the right half (two leaves) or the middle pair (four), any other truthy value the left half or the outer pair, as older layouts saved 1. `openValue` in `app.js` alternates the two on each opening (right/middle first; per visit, not saved), and validation keeps the 2.
- A cabinet design is a tree: a column holds stacked rows (`cells`), a row may hold side-by-side `parts`, and a part may hold stacked `cells` again, to any depth. Rows and parts without children are the cells with fronts, finishes and open states. `cabinetStructure` walks the tree into cell rects (`insetL`/`insetR` give the board at each side: a side panel at the column's edges, half a divider inside) plus `rowLines` and `partLines`; dividers run the full height of their row and every shelf, top board and back stops at a side panel or divider. Code that needs every front, open state or finish walks `designLeaves`/`findLeaf`; editing goes through `locateCell`, `splitCabinetCell` (the original half keeps the id), `removeCabinetNode` (a container left with one plain cell collapses into it, keeping its id), `moveCabinetLine`, and `fitDesign`, which makes nested rows and parts fill their space again on the side that changed. Splitting keeps ids so open states and niche TVs stay attached; editor actions that would remove a cell holding a niche TV are refused with the TV's name, and a TV whose cell is gone anyway is not drawn and keeps its warning.
- A robot-vacuum cabinet uses two cabinet options: a raised floor column (`bottom` > 0) may set `sidesToFloor`, which draws its two side panels down to the floor and leaves the gap between them open, and a column's lowest cell may set `noBase`, which leaves out its bottom board so its space runs down through the gap to the floor. Validation keeps `sidesToFloor` only on raised floor cabinets and `noBase` only on lowest cells (a split keeps it on the lower or left half). `cabinetOccupiedRects` turns a `noBase` cell into open space (only its back panel stays solid, from the column's underside to the board above) and adds the two floor-reaching sides, so a `robotVacuum` (dock plus robot; the default is a Dreame X60 Ultra, 390 × 425 × 498 mm, whose lid needs about 30 cm above to open) can stand inside without a clash. The dock clashes as two boxes (`robotVacuumRects` in `geometry.js`, from `DOCK`, which `scene.js` also draws from): the 29.6 cm tower at full height and the ramp and robot in front only 10.5 cm high, so only the tower needs to fit in the cell and the robot may reach out under a raised cabinet. The properties panel then says `放在…內` instead of reporting the plan overlap (`housedIn` in `app.js`). A part standing on the floor must reach above `FLOOR_TOP` (0.8 cm): the dock's ramp plate first ended exactly there and z-fought with the floor in shifting white stripes. The gold edge strip is non-metallic, since metalness without an environment map renders almost black.
- Drawer units, vanities (`sink`) and kitchens are modular cabinets too (`cabinetTypes`; since 2026-09-27 they always carry a design, made from their door style on load, a drawer unit always drawers). A vanity's 10 cm top and a kitchen's 4 cm counter live in each column's `top` gap (`COUNTER` in `cabinet-design.js`); `validateCabinetDesign` puts it back after any edit, the top row absorbing the difference, `sinkTop`/`kitchenTop` in `scene.js` draw the top and fittings there, and `cabinetOccupiedRects` counts it as solid. The app validates the default layout at start-up, or a fresh visitor would get raw defaults with no designs.
- A fridge keeps its compartments in a `cabinetDesign` (always, from `fridgeDesign` layouts: 上冷藏下冷凍, 上冷凍下冷藏, 對開門, 法式多門, 三門) but is not in `cabinetTypes`: `makeFridge` in `scene.js` draws it (shell in `fridgeColor`, 5 cm fronts, bar handles, glass shelves, drawer bins, dark foot grille) and registers the same `modularCabinet` door/drawer parts, so opening, open-state saving and sweep checks work unchanged. `keepFridge` allows door and drawer fronts only and no gaps or missing bottoms. The cabinet editor shows a fridge mode (layout buttons, colour row instead of finishes, no plinth, bottom-board or handle options). Steel is a light low-roughness grey, not a metal: metalness renders dark without an environment map.
- Sockets (`outlet`) mark where outlets go for the designer or carpenter, not wiring. Kind and mount fix their size (`outletSize`); `placeOutlet` in `spatial.js` puts a wall socket flat on the nearest wall run or column face facing out (`wallMount`, skipping wall joints) and a top or cell socket on its host at `offsetX`/`offsetZ` in the host's axes, so `syncSupportedTvs` carries it along like a TV. A wall socket clashes with what stands or hangs in front of its wall (`socketCovered` in `geometry.js`: cabinet boards via `cabinetOccupiedRects`, a table or desk only by its top and legs, so under a desk is fine; rugs, lights, beams and other sockets never); the check is one-sided, so furniture never stops at a socket. `guardedSocket` in `spatial.js` stops a wall socket's move, raise or drag at contact along the straight path in x, z and height (1 cm steps, the plate being 1.5 cm thick) and refuses a turn or a change of mount that would bury it; `commitFurniture`, the top-view drag and the walk-view drag all go through it. On a back panel (`panel`) a wall socket is pushed out onto the panel face (`ontoPanels`, shared with wall TVs). Other sockets only report a missing host. In walk view (not the overview) a socket is dragged, or a new one placed by clicking, onto the surface under the pointer (`surfaceAt` in `scene.js`, `socketOnSurface` in `spatial.js`): an upright building face makes it a wall socket at that height, an upward face of a cabinet, desk or table a top socket, and a cabinet's front, door or inside the cell under the pointer (side panels are refused); a socket dropped into a closed cell opens that cell's door. In the cabinet editor a cell socket shows in the front drawing and can be dragged there. Top view draws a cell socket's ring above its cabinet's top. Every cabinet type now always carries a design (`alwaysModular` is `cabinetTypes`), or never-edited wardrobes could not take cell sockets. Kinds are 110 V duplex, with USB, and data/TV (220 V and pop-ups were dropped on 2026-09-27; saved ones load as duplex). The properties panel has only kind and height: where a socket sits comes from dragging it in walk view. A wall or back-panel socket turns in its plane (`spin`, any angle, shown in the rotation field as 牆面上的旋轉); its size is the turned plate's bounding box (`turnedSize`), and the plate turns as one piece, slots included, counterclockwise seen from the front, as a turn on a top is seen from above. A turn keeps the plate's centre in place (`turnAboutCentre`): `elevation` is the bottom of the turned box, so without it a turn kept the bottom fixed and the plate climbed; the rotation field and the +90 button go through it for sockets and wall TVs alike. `commitFurniture` deletes `spin`, `offsetRot` and the offsets when validation leaves them out, or a turn back to 0 (not stored) kept the old 270. Its arrow keys: the pair along the wall moves it, the pair across the wall (which cannot move it) raises (↑ →) and lowers (↓ ←) it. A socket on a top lies flat (the faceplate group turned face up, 1.2 cm thick) and may turn on its host (`offsetRot`); `commitFurniture` re-places a hosted socket from its typed or nudged position (`fromPoint`), or its stored offsets threw every typed move and turn away. A 12 cm plate is hard to find from above, so top view adds an orange ring just above it (not near the ceiling, or the selection box would reach up there). An unseen disc (`colorWrite` off) fills the ring so a click anywhere inside it picks the socket. A socket has no top-view resize edges (`resizeAtPointer` and `onResize` skip it): its kind fixes its size, and an edge drag once stretched one out of the wall. Since 2026-09-29 every mount follows the furniture rule: a move (a drag, a typed position, offset or height; `placeOutlet(...,{stop:true})`, which any `fromPoint` implies) stops at the edges of its wall (`wallMount` clamps along the run), cell or top, and at what covers it (`guardedSocket`); a turn (`spin` on a wall or back panel, `offsetRot` flat) turns in place about its centre, and a load or a host change leaves it where it is, so whatever it then overlaps or runs past is flagged by `issues` (與…重疊, 與牆體重疊, 超出牆面, 超出櫃格, 超出…的檯面／層板) as a red frame, never pushed back. `commitFurniture` skips `fitResize` and the size stop for a change of `spin` (`turning`): a turn changes the bounding box, not the size. A wall socket turned through the floor or ceiling is refused, like furniture crossing the outline. Wall TVs follow the same rule (`wallTvMount(...,{clamp})`, 超出牆面 in `issues`).

## Security & Configuration

Do not commit secrets or user-exported layout JSON. Browser state is stored per origin in `localStorage`. Loading validates the whole layout, and one invalid item makes the editor fall back to the initial layout, whose next autosave would overwrite the saved one; `setAside` in `recovery.js` copies the unreadable text first (key `a7-studio-v1-unreadable`), and autosave pauses if that copy fails. Still prefer loosening validation rules over tightening them. The A7 plan is public marketing material, not the owner's residence (confirmed 2026-09-11); no hosting access control is needed. Preserve `.openai/hosting.json` and the static `dist` publishing configuration.

Board finishes (`dist/finishes.js`, furniture) and floorings (`dist/floorings.js`, room floors; a second supplier's 2025 SPC catalogue, measured 2026-09-24) are modelled on supplier catalogues whose images are all rights reserved. Never commit or hotlink supplier images: store only measured colours and pattern types, and generate textures in code. The side-by-side comparison sheets live in the Dropbox project folder (`材質比對/`), not here.
